# Q&A controls

Default limits: 5 API calls per session/minute, 15 globally/minute, 100 globally/UTC day and a conservative 2,000,000 reserved-token daily budget. Each API attempt reserves 20,000 tokens; failures count, SDK automatic retries are disabled. These are conservative request/token quotas, not measured dollar spending. Set a provider-side spending limit as well; arbitrary configured models have different prices. All budgets are configurable through QA_SESSION_PER_MINUTE, QA_GLOBAL_PER_MINUTE, QA_DAILY_REQUESTS and QA_DAILY_TOKEN_BUDGET. Limits reserve transactionally in SQLite before API execution.

Exact question/model/API-key-fingerprint/data-content cache expires after one hour. Cached responses skip the API and its budget. Every relevant filter scope and numeric data value contributes to the fingerprint; no semantic similarity caching. Credentials themselves are not stored in this database. QA_DB_PATH must be on durable storage to retain budgets across deployment restarts. SQLite quotas apply to one shared database; independent replicas need a shared transactional service. Anonymous session limits can be bypassed by new sessions; global quotas still bound this host. Cached endpoints are not protected against general network denial of service.

Input screening rejects known instruction overrides, secret requests, SQL mutations, fabricated-number requests and some unsupported forecasts. This is a narrow heuristic, not comprehensive prompt-injection prevention. Pydantic enums and allowlisted parameterized SQL enforce execution boundaries even if interpretation is wrong. Refusal and semantic correctness still need human evidence review. Graph execution is bounded, with deterministic grounded output; no self-repair loop or additional agents spend more tokens.
